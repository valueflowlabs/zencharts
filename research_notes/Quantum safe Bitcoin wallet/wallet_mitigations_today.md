# What a Bitcoin wallet can do today, before a PQ soft fork (as of Oct 26, 2026)

Scope: wallet-level and user-level steps on today's consensus rules. BIP-360 internals and qubit estimates are left to other researchers. Searches ran on 2026-10-26. Some primary pages (projecteleven.com, the gnusha.org mirror of the bitcoin-dev list) returned HTTP 403, so a few points rely on secondary coverage. Those points are flagged.

## 1. Address hygiene: script types, reuse, and Taproot for long-term storage

### Takeaway
On today's rules, the best wallet-level protection against a long-range quantum attack is to keep funds in hash-committed outputs that have never been spent from: P2PKH, P2WPKH, P2SH or P2WSH, never reused. P2TR (and P2PK and bare multisig) exposes a key on-chain from the moment it receives funds. For long-term cold storage, avoiding P2TR key-path outputs is the defensible choice today. The cost is somewhat higher fees and a smaller anonymity set among Taproot users.

### Cited Findings
- Chaincode Labs report (Anthony Milton and Clara Shikhelman, May 2025): "P2PK, P2MS and P2TR are all vulnerable from the moment they receive funds, as they expose public keys directly in the output script." The other script types are vulnerable only "at the moment they are spent from." — [Chaincode, Bitcoin and Quantum Computing (May 2025), p.11](https://chaincode.com/bitcoin-post-quantum.pdf)
- On P2TR, the same report says the key path uses a "tweaked key". Because that key is on-chain, "a CRQC could potentially derive the corresponding private key, enabling unauthorized spending via the key-path without needing to satisfy any script conditions." It also says this "could be addressed through a soft fork that disables key-path spending." At the time, P2TR held ~32.5% of UTXOs but only ~0.74% of value (~146,715 BTC). — [Chaincode (May 2025), p.10–11](https://chaincode.com/bitcoin-post-quantum.pdf)
- Address reuse "transforms script types that would normally only be vulnerable to short-range attacks into ones that are vulnerable to long-range attacks". It is "particularly dangerous in a post-quantum environment." — [Chaincode (May 2025), p.12](https://chaincode.com/bitcoin-post-quantum.pdf)
- Spending a coin on a fork chain also exposes its public key. Spending a UTXO on Bitcoin Cash or Bitcoin Gold in 2017–2019 revealed the key for the matching, still-unspent BTC UTXO. — [Chaincode (May 2025), p.12](https://chaincode.com/bitcoin-post-quantum.pdf)
- Chaincode's recommended immediate measure: "vulnerable funds can be immediately migrated to somewhat quantum-resistant address types (P2PKH, P2SH, P2WPKH, or P2WSH). Simultaneously eliminating address reuse practices will prevent future exposure to long-range quantum attacks." — [Chaincode (May 2025), Appendix III, p.45](https://chaincode.com/bitcoin-post-quantum.pdf)
- Scale: Chaincode estimates "Approximately 20-50% of all Bitcoin in circulation (4-10 million BTC) is potentially vulnerable." — [Chaincode (May 2025), Appendix II](https://chaincode.com/bitcoin-post-quantum.pdf). Ledger Donjon (Feb 2026) puts it at about 25% by value with exposed public keys — [secondary summary of Ledger Donjon via search; Ledger blog](https://www.ledger.com/blog-quantum-computing-threat-to-blockchain). Jameson Lopp (Casa) estimated ~4M BTC (~25% of supply) — [Bitget news](https://www.bitget.com/news/detail/12560605461139). Coinbase's David Duong estimated 6.51M BTC and cited Project Eleven data that ~70% of vulnerable BTC comes from address reuse — [same source](https://www.bitget.com/news/detail/12560605461139). These estimates differ.
- Blockstream's quantum page lists P2PK and P2TR outputs, spent-from P2PKH/P2WPKH, and reused addresses as exposed, and says hashed addresses hide the public key until spend. It also warns that "Fast-clock quantum architectures make even briefly-exposed keys vulnerable." — [Blockstream, Bitcoin's Quantum Defense](https://blockstream.com/quantum/)
- Casa's wallet sends change to a new address and gives a fresh receive address every time. Mainstream HD hardware wallets (Trezor, Ledger, Coldcard) generate fresh addresses by default in the standard receive flow. — [Bitget summary of Casa/Lopp](https://www.bitget.com/news/detail/12560605461139)

### Inferences
- Practical rule for wallets: (a) default long-term storage to P2WPKH (single-sig) or P2WSH (multisig); (b) refuse or warn on address reuse; (c) after any spend, sweep the change and remainder to fresh addresses, so no UTXO is left on an address whose key was revealed. Many wallets already do (c) because change goes to a fresh address. The real danger is reused receive addresses, for example on exchange deposits or donation addresses.
- The Taproot trade-off: P2TR key-path spends are cheaper and more private, since a multisig looks like a single-sig and the P2TR anonymity set is large. For cold storage held for years, those benefits matter little next to permanent key exposure. For hot or spending wallets, P2TR is defensible, since coins move often and any PQ soft fork will come with a migration window.
- Chaincode notes the P2TR vulnerability "could be addressed through a soft fork that disables key-path spending". That rescues P2TR only if the output has a usable PQ script leaf, or if some seed-based proof (Section 4) is accepted. Plain BIP-86 key-path-only outputs would rely on the seed proof.
- "Hidden until spend" protects only against long-range attacks. Every script type is exposed while a spend is in flight (Section 3). Hash-type outputs also leak the key wherever it is shared off-chain (Section 2).

### Gaps
- I found no vendor (Trezor, Ledger, BitBox, Coinkite) document that formally recommends avoiding Taproot for cold storage because of quantum risk.
- There is no authoritative, current (Oct 2026) figure for exposed BTC. The estimates above range from ~4M to 10M BTC.

## 2. xpub exposure and coordinator designs

### Takeaway
An xpub is a public key plus a chain code. Anyone holding it (watch-only servers, Electrum or other indexers, multisig coordinators, accounting or tax tools, payment processors) can compute every non-hardened child public key. A future CRQC holder with the xpub could therefore derive every non-hardened child private key, so all "hidden" hash-type addresses under that xpub are effectively exposed. Hardened children stay safe. Wallets should treat xpubs and descriptors as secrets and keep sharing to a minimum.

### Cited Findings
- "A quantum computer with access to an xpub and its chain code could derive, through simple iteration, all non-hardened child public keys, and thus all corresponding private keys. This creates a cascading vulnerability where a single exposed xpub could compromise all funds held in non-hardened derivation paths (hardened child keys remain secure)." — [Chaincode (May 2025), p.12](https://chaincode.com/bitcoin-post-quantum.pdf)
- Chaincode notes that exchanges, wallet providers, payment processors and custody solutions commonly require customers to share xpubs, and that CRQCs "fundamentally change the xpub security model." — [Chaincode (May 2025), p.12](https://chaincode.com/bitcoin-post-quantum.pdf)
- If xpubs are kept private, CRQCs add no new linkability: "CRQCs can't be used to reveal links between addresses derived from the same (private) xpub." The derivation direction (child to parent) rests on hash functions, not ECC. — [Chaincode (May 2025), p.12](https://chaincode.com/bitcoin-post-quantum.pdf)
- Chaincode lists "the security of xpub sharing", along with hardening practices and derivation paths, as a factor in how much risk a holder carries. — [Chaincode](https://chaincode.com/bitcoin-post-quantum.pdf)
- A Delving Bitcoin discussion of the Chaincode report includes avoiding xpub sharing among its mitigations. — [Delving Bitcoin, Bitcoin and Quantum Computing](https://delvingbitcoin.org/t/bitcoin-and-quantum-computing/1730) (secondary search snippet; thread not fully read)
- In the April 2026 seed-proof thread, conduition proposed rooting the proof at a hardened account-level key (e.g. m/86'/0'), with the unhardened steps checked outside the circuit. The hardened/unhardened boundary is what the PQ recovery relies on. — [bitcoin-dev, Osuntokun, Apr 8–9 2026](https://groups.google.com/g/bitcoindev/c/Q06piCEJhkI/m/6BN8qE3gAQAJ)

### Inferences
- An xpub held by a third party turns every address under it into a long-range target if that party's data leaks, now or later. Harvest-now-decrypt-later applies: a database of xpubs leaked today could be exploited by a future CRQC holder. Watch-only wallets connected to public Electrum servers usually send addresses or script hashes, not xpubs, though some backends and SaaS trackers ingest full xpubs or descriptors. Self-hosting the indexer (own node plus Electrum server) removes that third-party exposure.
- Coordinator designs that limit xpub sharing:
  - Self-hosted coordinators (Sparrow, Specter or Nunchuk against your own node) that never upload descriptors.
  - Encrypting descriptor backups at rest.
  - Giving a collaborative-custody provider only what it needs. In 2-of-3 or 3-of-5 multisig the provider (Casa, Unchained) normally holds the full descriptor to co-sign and monitor — [Casa/Unchained structure, spark.money comparison](https://www.spark.money/tools/bitcoin-multisig-service-comparison). That puts the descriptor's secrecy in the provider's hands.
  - Separate hardened accounts per counterparty, so a single leaked xpub exposes only that account.
- Descriptor or wallet-backup leaks (cloud backups, PDFs, QR codes) carry the same consequence: if the backup includes xpubs, it is a future long-range exposure even with no private keys in it.

### Gaps
- I found no published Casa or Unchained guidance specific to quantum risk and xpub handling. Searches returned only generic multisig comparisons.
- I found no wallet that markets "xpub-less" watch-only as a quantum measure.

## 3. Mempool (short-range) exposure during spends

### Takeaway
Every script type exposes its public key once a spend is broadcast. Until confirmation, plus a reorg-depth margin, a CRQC fast enough to break a key within that window could double-spend. Private or direct-to-miner submission narrows the window but means trusting the miner and creates a two-tier broadcast system. It is a partial mitigation, not protection.

### Cited Findings
- "When the transaction is in mempools across the network, these public keys(s) are open for all to see, so an attacker with a CRQC could potentially derive the corresponding private key(s) and then sign and broadcast a competing replacement transaction, or could directly mine it without broadcasting… or… do a chain reorg." — [Chaincode (May 2025), p.11](https://chaincode.com/bitcoin-post-quantum.pdf)
- Short-range attacks "affect all Bitcoin script types… requiring attackers to act within a timeframe of minutes to hours." — [Chaincode, Appendix II](https://chaincode.com/bitcoin-post-quantum.pdf)
- Private transaction services such as MARA's Slipstream "allow users to submit transactions directly to trusted miners rather than broadcasting them publicly." Chaincode says this "could reduce, but not eliminate, risks," that "Users need to trust that such services would not use a CRQC to steal their funds," and that these services are already "contentious" (non-financial data storage, two-tier broadcast). — [Chaincode (May 2025), p.35](https://chaincode.com/bitcoin-post-quantum.pdf)
- Blockstream warns that "fast-clock" quantum architectures make "even briefly-exposed keys vulnerable." — [Blockstream quantum page](https://blockstream.com/quantum/)

### Inferences
- Wallet-level measures today: pay competitive fees so the transaction confirms in the next block; avoid low-fee RBF chains that sit in the mempool for hours; optionally submit directly to a large miner's private pool; consolidate rarely, but sweep fully when you do spend (no leftover UTXOs on exposed keys).
- Once a PQ output type exists, the migration spend itself is a short-range event. Wallets will want private submission or fast-confirmation fee policy for the migration transaction, especially for large holdings.
- Short-range attacks need a CRQC that breaks a key in minutes to hours. That is generally treated as a later-stage threat than long-range attacks on exposed keys. Timelines are out of scope here.

### Gaps
- I did not find current (2026) data on the share of hashrate offering private submission, or any wallet with built-in "quantum-aware" private broadcast.

## 4. Preparing for migration: BIP-32 seed proofs and commit-reveal

### Takeaway
The most valuable thing a user can do today is keep the BIP-39/BIP-32 seed (and passphrase) that generated their coins, with coins on standard derivation paths. Several 2025–2026 proposals and prototypes (Osuntokun's zk-STARK of BIP-86 derivation, Project Eleven's faster prototype, conduition's hardened-xpriv variant) would let owners prove seed knowledge without ECDSA or Schnorr if key-path or ECDSA spending is later disabled. Coins from non-HD keypool wallets, imported WIF keys, brainwallets and P2PK are not covered. Commit-reveal schemes (Dryja's "Lifeboat"/Fawkescoin variant, Commit-Delay-Reveal) need a future soft fork. I found no evidence that a wallet can make a consensus-binding commitment today.

### Cited Findings
- **Osuntokun prototype (Apr 8, 2026):** a zk-STARK proving that a Taproot output key was derived from a BIP-32 seed along a BIP-86 path, with seed and path as private witness. The goal is a PQ exit for BIP-86 wallets if keyspend is disabled. v1: ~55 s to prove on M4 Max, ~12 GB RAM, ~1.7 MB proof, ~1.8 s to verify. With recursion (Apr 9) the proof is ~200 KB but takes ~180 s to prove. Limitations noted: it does not yet commit to a txid or sighash; it depends on a future soft fork; Bitcoin Core's original keypool (non-HD) wallets are not covered, and the author suggests moving those coins to a BIP-32 wallet. — [bitcoin-dev, Osuntokun (Apr 2026)](https://groups.google.com/g/bitcoindev/c/Q06piCEJhkI/m/6BN8qE3gAQAJ)
- **conduition's replies (Apr 8, 2026):** prove knowledge of a hardened xpriv (e.g. m/86'/0') and check the rest outside the circuit, which could cover many UTXOs in one proof. Output a child xpriv, which costs roughly two SHA-512 compressions. Commit-reveal is a lighter alternative ("a few hundred bytes across two transactions"). — [same thread](https://groups.google.com/g/bitcoindev/c/Q06piCEJhkI/m/6BN8qE3gAQAJ)
- **Project Eleven prototype (reported Jul 19, 2026):** proves the holder has key material above the address in the derivation tree and binds the proof to a message such as a migration transaction. Built with Jim Posen (Binius). 243 ms to prove on 4 cores and 40 ms to verify on an M5 MacBook Air, ~2 GB RAM, no GPU, no trusted setup. Limitations: unaudited and incomplete; rooted at the coin-type key rather than the seed; supports three address types but not Taproot; recovers nothing on any live chain. — [CoinDesk, Jul 19 2026](https://www.coindesk.com/tech/2026/07/19/bitcoin-s-quantum-problem-gets-a-recovery-tool-but-not-for-satoshi-s-1-1-million-coin)
- **Who is excluded:** pre-BIP-32 wallets "generated every key independently and at random". Satoshi's P2PK coins have "no seed phrase, derivation path, or parent key", so there is no tree to prove. — [CoinDesk, Jul 2026](https://www.coindesk.com/tech/2026/07/19/bitcoin-s-quantum-problem-gets-a-recovery-tool-but-not-for-satoshi-s-1-1-million-coin)
- **Chaincode on HD seed proofs:** "For HD wallets, users can prove knowledge of master seeds that generate specific address hashes, enabling recovery even when individual private keys are lost," which extends protection "to practically all Bitcoin created since HD wallets became standard." This "would require consensus on integrating relatively novel zero-knowledge proof systems." The same section describes "signature lifting", a PICNIC-based ZK proof of the key behind a hashed address. — [Chaincode (May 2025), p.33–34](https://chaincode.com/bitcoin-post-quantum.pdf)
- **Commit-Delay-Reveal (2018 origin):** the user commits (hash of ECDSA pubkey plus PQ pubkey) in a transaction, waits a mandated delay (6 months suggested), then reveals both keys. It needs a soft fork to make commitments binding. Fees for the commitment must be paid from quantum-resistant funds. — [Chaincode (May 2025), p.33](https://chaincode.com/bitcoin-post-quantum.pdf)
- **Dryja:** proposed a "Post-Quantum commit / reveal Fawkescoin variant as a soft fork" on bitcoin-dev (May 28, 2025), reported under the name "Lifeboat". No implementation timeline. — [bitcoin-dev thread](https://groups.google.com/g/bitcoindev/c/LpWOcXMcvk8/m/DjaiWnViAQAJ); [Crypto Briefing](https://cryptobriefing.com/bitcoin-quantum-attack-recovery-tool/). Bitcoin Optech lists commit/reveal post-quantum recovery as a July 2025 topic. — [Optech topic dates](https://bitcoinops.org/en/topic-dates/)
- **Lopp:** argued in March 2025 against recovery mechanisms, preferring that vulnerable coins effectively be burned. — [Crypto Briefing](https://cryptobriefing.com/bitcoin-quantum-attack-recovery-tool/). BIP-361, published April 2026 by Lopp and five co-authors, would block new deposits to vulnerable addresses after 3 years and freeze the rest after 5. It is a proposal, not active. — [CoinDesk](https://www.coindesk.com/tech/2026/07/19/bitcoin-s-quantum-problem-gets-a-recovery-tool-but-not-for-satoshi-s-1-1-million-coin)
- **Kurbatov (Delving Bitcoin):** ZK proofs that let P2PKH owners prove key knowledge without revealing the public key, plus a PQ signature, to mark outputs as migrated. — [search snippet referencing Delving Bitcoin](https://postquantum.com/quantum-threat-crypto/fixing-bitcoin-pqc-migration/) (secondary)
- **Off-chain registry (Project Eleven Yellowpages, launched June 2025):** users generate hybrid/PQ key pairs, create a proof linking them to existing BTC addresses, and timestamp it in an off-chain registry. No on-chain transaction. — [The Quantum Insider, Jun 19 2025](https://thequantuminsider.com/2025/06/19/project-eleven-raises-6-million-to-secure-digital-assets-against-quantum-threats/). Secondary blogs describe it as the "only" deployed PQ solution for Bitcoin. That is a promotional claim. — [BlockEden](https://blockeden.xyz/blog/2026/05/01/project-eleven-20m-series-a-post-quantum-bitcoin-yellowpages/). The primary page (projecteleven.com/blog/hello-yellowpages) returned 403.

### Inferences
- What wallets can do now:
  - Generate coins only from BIP-39/BIP-32 seeds on standard BIP-44/49/84/86 paths, and record the path or descriptor.
  - Warn users who hold coins on imported WIF keys, legacy keypool wallets (pre-0.13 Bitcoin Core), brainwallets or P2PK, and suggest sweeping them to an HD wallet while ECDSA is still safe. Osuntokun explicitly suggests this for keypool wallets.
  - Keep seed backups durable: metal backups, documented passphrase, inheritance plan. A seed proof can recover coins only if the seed survives the years until a soft fork.
- BIP-39 passphrases fit within this approach, since the passphrase is an input to the seed. Users must keep the passphrase, because any proof needs the exact seed.
- Proof-of-knowledge here works at the seed or hardened-xpriv level. Revealing that material in a non-ZK way would expose other unmigrated UTXOs under the same seed, which is why the ZK variants matter. A search snippet, possibly drawn from the [Roasbeef work-tracker gist](https://gist.github.com/Roasbeef/563f173fe44e2005e003a082716e586f), said an earlier design using BIP-32 as the one-way function into Picnic "reveals the secret BIP-32 seed". I did not verify this in a primary source. Chaincode's description of signature lifting says it works "without ever revealing that quantum-vulnerable public key".
- Multisig nuance: spending from a P2SH or P2WSH multisig reveals the full redeem or witness script, so every cosigner's pubkey for that address is exposed, not only the keys that signed. Fresh addresses per receive, with change swept to new addresses, therefore matter as much for collaborative custody (Casa, Unchained style) as for single-sig.
- **Commitments today:** no proposal I found gives consensus weight to commitments made before its activation. CDR and Lifeboat both define the commitment as a transaction under new rules. Off-chain timestamps (Yellowpages, OpenTimestamps of a PQ pubkey) have no consensus standing. Their value depends on a future soft fork choosing to honour such pre-commitments, which none of the cited proposals currently does. Treat them as speculative.
- **Coins most at risk of being stranded:** pre-2012 keys, imported keys and brainwallets cannot use any seed proof. Brainwallets are also cracked classically. Owners who expose a public key, through P2TR or reuse, and lose the seed lose both routes.

### Gaps
- I could not confirm which three address types the Project Eleven prototype supports. CoinDesk does not name them.
- I found no wallet vendor that has announced a "seed proof readiness" feature, such as exporting derivation metadata for a future prover.
- The 2026 status of Dryja's Lifeboat beyond the 2025 post is unknown.

## 5. Taproot script trees with a PQ leaf committed today

### Takeaway
Tim Ruffing (Blockstream Research, July 2025, ePrint 2025/1307) proved that Taproot's commitment to its script tree is binding and hiding against quantum adversaries in the QROM. A PQ fallback leaf committed today could therefore still be trusted after a future soft fork disables key-path spends. The catch is that Bitcoin has no PQ signature opcode today, and the safe way to put a "future" leaf into a tree is unresolved. Corallo's plan, and Ruffing's proof that supports it, is a protocol path. It is not something wallets can safely ship on today's rules.

### Cited Findings
- Ruffing, "The Post-Quantum Security of Bitcoin's Taproot as a Commitment Scheme" (eprint 2025/1307): concrete upper bounds on a quantum adversary breaking binding or hiding. On binding, an attacker with a quantum computer "can't create a Taproot output that can be 'opened' to an unexpected Merkle root" (QROM). On hiding, the attacker "learns nothing about the Merkle root (until it is revealed)." — [ePrint 2025/1307](https://eprint.iacr.org/2025/1307); [bitcoin-dev post "Taproot is post-quantum secure when restricted to script-path spends"](https://gnusha.org/pi/bitcoindev/bee6b897379b9ae0c3d48f53d40a6d70fe7915f0.camel@real-or-random.org/t/) (mirror 403; summarized via search)
- The plan this supports: a first soft fork adds PQ signature opcodes usable in tapscript, and a later one disables Schnorr/ECDSA key-path spending once a CRQC is imminent. Users then spend via the PQ leaf. The idea is credited to Matt Corallo. — [Bitcoin Magazine, Sep 19 2025](https://bitcoinmagazine.com/technical/bitcoins-quantum-risk-is-real-one-solution-might-start-with-taproot)
- Bitcoin Magazine says users cannot use such a leaf under current rules. Step 1 is adding PQ opcodes, and which PQ algorithms to use remains open. PQ signatures are 40–600× larger, and threshold PQ signatures are an open research problem. — [Bitcoin Magazine](https://bitcoinmagazine.com/technical/bitcoins-quantum-risk-is-real-one-solution-might-start-with-taproot)
- Chaincode notes that P2TR vulnerability "could be addressed through a soft fork that disables key-path spending (see Lamport Signatures with OP_CAT, Quantum-Secure Taproot Scripts)." — [Chaincode (May 2025)](https://chaincode.com/bitcoin-post-quantum.pdf)
- Blockstream Research (2026): first PQ-signed transaction on Liquid, March 3, 2026, using SHRINCS (324-byte hash-based signatures) via Simplicity. In Q2 2026 Blockstream proposed OP_CHECKSHRINCS for Bitcoin. — [Blockstream quantum page](https://blockstream.com/quantum/); [Blockstream on X, Q2 recap](https://x.com/Blockstream/status/2073038914932113513)

### Inferences (flagged: reasoning from tapscript rules, not from a sourced statement)
- Under BIP-342, a tapscript leaf containing an OP_SUCCESSx opcode, or using an unknown leaf version, is anyone-can-spend today. A wallet that commits a "future PQ opcode" leaf on today's rules risks creating an output that anyone who learns the leaf can spend now. Wallets should not do this.
- A leaf that only commits a hash of a future PQ public key, with a currently unsatisfiable script, is safe but inert. It becomes meaningful only if a future soft fork chooses to give such leaves meaning, and no current proposal I found does. Its value today is speculative and probably near zero.
- The Ruffing result matters most for P2TR outputs created after a PQ opcode activates, or for whatever a future BIP-360 output type (P2MR/P2QRH, out of scope) standardizes. For today's BIP-86 key-path-only outputs, the realistic rescue route is the seed proof in Section 4.
- Hunter Beast (BIP-360 author): I found no direct statement of his on "commit a PQ leaf today" in this pass. BIP-360 details are covered by other researchers.

### Gaps
- I could not read the bitcoin-dev replies to Ruffing (mirror 403), so I have no direct quotes from Corallo or Hunter Beast.
- I found no wallet that ships a "PQ fallback leaf" product.

## 6. What existing products and vendors actually ship, plus scams and disclosures

### Takeaway
As of Oct 2026, no Bitcoin wallet can make bitcoins quantum-safe, because consensus has no PQ signature. Shipped PQ features protect the device, not the coins: Trezor Safe 7 uses SLH-DSA secure boot and an ML-DSA device certificate. Other offerings are off-chain registries (Project Eleven Yellowpages), research prototypes (seed-proof STARKs) or sidechain demos (Blockstream SHRINCS on Liquid). Treat any "quantum-proof Bitcoin wallet" marketing, and any unsolicited "quantum vulnerability" email, as suspect.

### Cited Findings
- **Trezor (CTO Tomáš Sušánka, Mar 16 2026):** Safe 7 verifies the bootloader at every start with SLH-DSA-128, with firmware-update verification "planned in the following months". The device certificate is signed with ML-DSA-44, but this is "not yet fully implemented in firmware and Suite". The bootloader public key and certificate are fixed at the factory. Trezor states plainly that no wallet can make crypto fully quantum-proof today, and that Bitcoin, Ethereum and Solana are not quantum-secure. It markets the Safe 7 as the "first quantum-ready hardware wallet". — [Trezor blog](https://trezor.io/blog/security/what-quantum-ready-crypto-security-means-and-why-it-matters); [Trezor guide](https://trezor.io/es/guides/trezor-devices/trezor-safe-7/the-first-quantum-ready-hardware-wallet)
- **Ledger:** CTO Charles Guillemet says no quantum computer able to break Bitcoin exists, and urges migration ahead of the threat. The Ledger Donjon (Feb 2026) analysis put ~25% of BTC by value as having exposed public keys. An April 2026 Donjon post showed side-channel attacks on open-source PQ code ("40 EM traces within a minute"), which shows PQ on hardware wallets needs hardened implementations. Ledger's X account (Jun 2026) calls such computers "still theoretical". Ledger cites its "modular architecture" for future PQ support but has not shipped a Bitcoin PQ feature. — [Ledger blog: quantum threat](https://www.ledger.com/blog-quantum-computing-threat-to-blockchain); [Ledger blog: side-channel & PQC](https://www.ledger.com/blog-risk-side-channel-attacks-post-quantum-cryptography); [Guillemet on X](https://x.com/P3b7_/status/2027381020568223780); [CryptoTimes, Apr 23 2026](https://www.cryptotimes.io/2026/04/23/crypto-faces-y2k-scale-crisis-says-ledger-cto-amid-quantum-push/) (summaries via search)
- **A fabricated product claim:** one aggregator site claims a "Ledger Nano X Pro" with CRYSTALS-KYBER quantum resistance, "first consumer wallet certified". I found no such product. This looks like AI-generated or invented content to avoid. — [ProTrader Daily (unreliable)](https://protraderdaily.com/crypto/best-bitcoin-wallet-2026)
- **BitBox:** I found no quantum-specific feature. The BitBox02 Nova has an EAL6+ secure chip and a Bitcoin-only edition. — [bitcoin-mastery / hardware wallet roundup](https://bitcoin-mastery.com/article/best-bitcoin-hardware-wallets-2026)
- **Coinkite/Coldcard:** I found no quantum statement. Unrelated to quantum but relevant to seed hygiene: 2026 reporting describes a firmware bug dating from March 2021 that bypassed the hardware RNG during key generation, with ~1,816 BTC (~$116M) reported stolen from 5,200+ addresses. The fix is in later firmware. — [TRM Labs](https://www.trmlabs.com/resources/blog/the-largest-hardware-wallet-exploit-of-2026-inside-the-usd-116-million-coldcard-hack); [The Hacker News, Aug 2026](https://thehackernews.com/2026/08/coldcard-hardware-wallet-flaw-linked-to.html) (figures as reported, not independently verified)
- **Blockstream:** SHRINCS PQ transaction on Liquid (Mar 2026), the OP_CHECKSHRINCS proposal (Q2 2026), and Jade now a three-model lineup. Secondary summaries say PQ will reach Jade via firmware update, with no date found. — [Blockstream quantum](https://blockstream.com/quantum/); [Blockstream X](https://x.com/Blockstream/status/2073038914932113513)
- **Casa (Lopp):** public advocacy against address reuse. Casa wallets use fresh addresses for receive and change. ### Inferences
- Red flags for "quantum-safe Bitcoin wallet" marketing: any claim that coins on Bitcoin L1 are quantum-safe today (impossible without a soft fork); requests to move coins to a "quantum vault" controlled by a third party; requests to enter a seed to "upgrade"; new "quantum-proof" tokens or forks. Legitimate vendor features today cover device integrity (boot or firmware PQ signatures), address hygiene defaults, and future firmware upgradability.
- Hardware wallets matter for migration because the eventual PQ signature schemes (ML-DSA, SLH-DSA, SHRINCS or similar) have large keys, signatures and state. Devices need enough memory and flash, plus side-channel-hardened implementations (see Donjon's results), and a PQ-signed firmware chain so a quantum attacker cannot push malicious firmware. That is the real security value of Trezor's SLH-DSA secure boot.

## 7. Lessons from chains that already shipped PQ wallets

### Takeaway
Chains that shipped PQ wallets show recurring problems: hash-based one-time or stateful signatures force strict key rotation and state management; opt-in features see little uptake; hardware-wallet support lags the protocol. Bitcoin wallets should design for state management, larger signatures and firmware upgradability now.

### Cited Findings
- **Solana Winternitz Vault (Dean Little, Jan 2025):** opt-in vault using hash-based one-time signatures. Each spend uses fresh keys and the vault closes, so a new address is needed per transaction. Not a default chain feature. — [The Quantum Insider, Jan 4 2025](https://thequantuminsider.com/2025/01/04/solana-takes-a-step-toward-pqc-era-with-quantum-resistant-vault/); [Decrypt](https://decrypt.co/299511/sol-quantum-resistant-what-mean?amp=1)
- **Algorand (Falcon):** state proofs and Falcon signatures. The first mainnet Falcon-authorized transaction used a LogicSig. The roadmap targets native Falcon-1024 and hybrid accounts (Q3 2026 release) and broad quantum resilience by 2027. Algorand admits "End users will not have Falcon-capable hardware devices at this initial release." — [Algorand PQ roadmap](https://algorand.co/blog/algorand-post-quantum-cryptography-roadmap); [Decrypt](https://decrypt.co/371581/algorand-plans-ready-quantum-computing-threat-end-2027)
- **QRL (XMSS):** each signature uses up a WOTS+ one-time key in the XMSS tree, and the network rejects reuse of an OTS index. Wallets must track state. QRL 2.0 audit was planned for Q1 2026. — [QRL](https://www.theqrl.org/index.md); [QRL blog](https://theqrl.org/blog/statefulness-and-security)
- **Ethereum account abstraction:** an ERC-4337 Falcon verifier contract allows PQ wallets without consensus changes ("FalconSimpleWallet"). There is a Falcon-verification EIP from BTQ. A proposal to upgrade any wallet via a ZK proof of a hidden pubkey drew the objection that EIP-7702 authorizations can be overwritten by an ECDSA signature, so the ECDSA backdoor persists. EIP-8141 "Validation Frames" is reportedly in the works. — [ethresear.ch AA thread](https://ethresear.ch/t/the-road-to-post-quantum-ethereum-transaction-is-paved-with-account-abstraction-aa/21783); [ethresear.ch PQ signature thread](https://ethresear.ch/t/so-you-wanna-post-quantum-ethereum-transaction-signature/21291); [ethresear.ch ZK upgrade](https://ethresear.ch/t/upgrade-any-ethereum-wallet-to-post-quantum-security-in-one-transaction-using-zk-proofs-with-a-hidden-public-key/24754); [BTQ](https://btq.com/news/publishing-the-eip-for-falcon-verification)

### Inferences
- The Ethereum 7702 objection mirrors Bitcoin's Taproot key-path problem. A PQ path adds no security while a classical path to the same funds remains. The classical path must be disabled by consensus (Bitcoin), or the account must have no ECDSA root (Ethereum). Wallet "PQ features" layered on a live ECDSA key give users a false sense of safety.
- If Bitcoin adopts stateful or few-time hash-based signatures (SHRINCS-style or Winternitz-style), wallets will need robust state tracking. Seed-only restore could fail to reconstruct state without extra metadata, which matters for backup design. QRL's and Solana's one-time-key models show what that costs in practice.
- Hardware lag (Algorand) suggests Bitcoin hardware-wallet PQ signing will trail any soft fork. Devices with PQ-signed firmware chains and enough resources (Trezor Safe 7, Jade's upgrade path) are better positioned.
